## Подготовленные дополнительные изменения

### 1. Блокировка публикации до mobile

В `.github/workflows/deploy-public-site.yml`:

```diff
-    needs: verify
+    needs: [verify, mobile]
```

Ранее push в main мог опубликовать сайт после verify, пока mobile ещё работал или уже завершился ошибкой. Теперь публикация требует успеха обеих задач. Текущий workflow запускает публикацию автоматически при push в main; поэтому разрешение на слияние в main одновременно означает разрешение на последующую публикацию этим workflow.

### 2. Проверка совместной работы в браузере

В `tests/e2e/mobile.mjs` прежний полный маршрут certification вынесен в `checkCertificationIntegration`. Все прежние негативные проверки сохранены. Функция вызывается для desktop и мобильного профиля iPhone 13 в Chromium и WebKit.

Дополнительно проверяются:

- фактически сохранённые отрицательные flags, `q=null`, `tensor.Q=null`, `decision=null`, `readiness_scope=technical-package-only` и все verification=false;
- полное сохранение SC-5 JSON после прохождения certification;
- полное сохранение JSON досье после повторного реального маршрута Chronos;
- общий порядок в мобильном контексте: Chronos → certification → Chronos.

Эти новые браузерные утверждения подготовлены, но локально не исполнены. Результат их CI не предрешён.

## Последовательность интеграции

Предпочтительный путь — один интеграционный PR с текущего main: изменения №39, затем №45, затем две описанные правки. Это позволяет проверить весь кандидат до первого изменения и публикации main. Исходные PR остаются открытыми до отдельного решения автора.

1. Получить одобрение автора на публикацию этого конкретного кандидата в отдельной ветке и открытие интеграционного PR; это ещё не разрешение на слияние.
2. Перед созданием ветки повторно сверить три исходных SHA. При изменении любого ref пересчитать кандидат и заново проверить его.
3. На опубликованном кандидате потребовать успешные verify, mobile (Chromium и WebKit) и Links. Проверить точный SHA головы и тестируемый GitHub merge ref; после любого изменения повторить CI.
4. Проверить обновление уже установленного SW со старой revision, сохранение обоих журналов, восстановление страницы и отсутствие ложных полномочий. Выполнить отдельную smoke-проверку на физическом iPhone, если заявляется поддержка устройства.
5. Показать автору финальный diff и CI; запросить и дождаться отдельного одобрения слияния и автоматической публикации. До этого main не менять.
6. После одобрения и интеграции проверить опубликованные игру, certification, SC-5 и новый SW. Проверка workflow сейчас контролирует HTTP/HTML только корня и SC-5; она не заменяет функциональную smoke-проверку.

Если требуется сохранить именно отдельные слияния №39 и №45, сначала отдельной согласованной правкой установить `needs: [verify, mobile]`, затем обновить №39 от main и прогнать CI; после его одобренного слияния обновить №45 от нового main и повторить полный CI объединённого состояния. Каждый push в main потенциально публикует сайт и требует соответствующего одобрения.
